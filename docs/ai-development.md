# AI活用・開発運用

AI活用、外部ツール、レビュー、知見退避ルールをまとめる文書です。

`GitHub Copilotのススメ` と `GitHub Copilot プロンプトリファレンス [2026年1月版]` の知見を踏まえ、AIに実装を任せる範囲が広がっても、目的・完了条件・検証・権限範囲を明文化して安全に進める。

## 運用ルール（常時適用）

- ドキュメントのSSOTを明確化する。進捗は [PLAN.md](../PLAN.md)、構成/データモデルは [ARCHITECTURE.md](../ARCHITECTURE.md)、リポジトリ固有のAI実行ルールは [CLAUDE.md](../CLAUDE.md) / [.github/copilot-instructions.md](../.github/copilot-instructions.md)、AI運用チェックリストはこの文書を正とする。内容が矛盾した場合は、実行ルールとして [CLAUDE.md](../CLAUDE.md) / [.github/copilot-instructions.md](../.github/copilot-instructions.md) を優先し、この文書を同期更新する。
- Firebase Rules、App Check、Auth、世帯参加/解除、認証解除、課金、暗号化などのセキュリティ/プライバシー影響がある変更は人間レビューを必須とする。
- AI/外部ツール利用時は、本番の家計明細・秘密情報・認証情報を渡さない。
- 大きい実装や曖昧な依頼では、AI着手前に目的、参照ファイル、制約、期待する出力形式、完了条件、実行すべき検証を明示する。
- 仕様・設計・テスト観点を先にMarkdownへ残し、その文書をAI実装時のコンテキストにする。
- 実装で分かった仕様差分は、コードだけでなく [PLAN.md](../PLAN.md)、[ARCHITECTURE.md](../ARCHITECTURE.md)、ADR、チェックリストへ戻す。
- 重要な設計判断、方針転換、採用/不採用理由は [docs/decisions/](decisions/README.md) に記録し、将来の復活判断に必要な背景と復元方針も残す。
- 長いAI作業セッションで得た判断や再利用知見を、会話に閉じ込めず [PLAN.md](../PLAN.md)、repo memory、または専用ドキュメントへ退避する。
- CopilotコードレビューやAIによる脆弱性検出は補助として使い、最終判断は人間レビュー、テスト、lint、型チェック、Rulesテスト、Dependabot/secret scanning/code scanningなどの決定的チェックと併用する。
- Agent mode、Copilot CLI、Coding agentへ委任する場合は、Issue/タスク、変更範囲、禁止範囲、DoD、必須テスト、ドキュメント更新要否を明記してから実行する。
- 繰り返し使う作業手順（実装、レビュー、デバッグ、リリース確認、TestFlight検証）は、必要に応じて `.github/prompts/*.prompt.md` など再利用可能なプロンプトとして整備する。Copilot CLI / VS Code エージェントモードの使い分けは [docs/copilot-cli-workflows.md](copilot-cli-workflows.md) に集約する。
- 各リリース判定ゲートについて、必須テスト、実機確認、ドキュメント更新、ユーザー確認項目、未解決リスクのチェックリストを定義し、運用時に更新する。
- プロンプト自体が重要成果物になる場合は、AIに曖昧さ、定義不足、矛盾、隠れた前提をレビューさせてから使う
- 認証/認可、Security Rules、世帯所属、データ削除、課金、並行処理、オフライン同期に触る変更は、着手前に「[高リスク変更の進め方](#高リスク変更の進め方)」に従う。

## 高リスク変更の進め方

認証/認可、Firestore Security Rules、世帯所属、データ削除、課金、並行処理、オフライン同期に触る変更に適用する。2026-08-03の「所属済みユーザーが起動時に世帯未所属と誤判定される」修正で、状態遷移とRulesの評価時点を固定しないまま実装を始め、監査のたびにRulesの迂回・競合が見つかって修正と再監査を繰り返した反省による。

### 実装前に固定する

短い表で先に決める。この表が書けないうちは実装を始めない。

| 観点 | 固定する内容 |
| --- | --- |
| 状態 | 例: 未所属、承認待ち、active member、解除済み、世帯削除後 |
| 操作 | 例: 世帯作成、参加申請、承認後の所属確定、退出、プロフィール削除、世帯全削除 |
| Rules時点 | 各判定を、コミット前の `get()` とコミット後の `getAfter()` のどちらで行うか |
| 不変条件 | 競合、再試行、途中失敗が起きても守る条件 |
| テストと人間確認 | 許可する遷移と拒否する遷移をどのテストで担保するか、実機で人間が確認する項目は何か |
| 範囲 | 変更する対象、変更しない対象、必要な人間レビュー |

### 実装と独立監査は1回ずつ

1. 上の表に対応するRulesテスト・ユニットテストを先に追加する。
2. 範囲を固定した1回の実装バッチで変更する。密結合な変更を複数の実装担当へ細分化しない。
3. `npm test`、`npm run lint`、Rules変更時は `npm run test:rules` などの機械的ゲートを通す。
4. 独立監査（`auditor` エージェントなど別コンテキストの監査）は、機械的ゲート通過後に1回だけ行う。

「実装 → 監査 → 追加修正」を繰り返さない。監査で基本設計の欠落が見つかった場合は、同じ論点の監査を反復せず、上の表とテストを更新して再計画として扱い、修正後の最終監査まで進める。

### Rulesの迂回・並行競合はRulesテストで担保する

実機では踏めない経路は、[dev-clientでの動作確認](development-setup.md#dev-clientでの動作確認)の人間チェックリストへ足さず、`firestore.rules.test.ts` の拒否ケースとして書く。2026-08-03に実際に見つかった型は次のとおり。

- active member が `users.householdId` を先に消去・差し替えてから、別世帯作成やプロフィール削除へ進む逐次迂回
- 同一バッチで、新世帯への所属と別世帯への参加申請を同時に作る迂回
- 承認待ちの間に、別世帯への所属が確定する競合
- 古い所属判定が、後から書かれた新しい `householdId` を消す競合
