# 初回表示レイテンシと版チェックのサーバー往復（2026-07-25）

## 背景

バージョン1.0.2のTestFlight確認で、履歴・集計・履歴検索の初回表示に体感できるタイムラグがあると報告された。ユーザーからの提案は「端末キャッシュを先に表示して、バックグラウンドで更新確認し、更新があれば差し替える」。

調査したところ、cache-first + background-revalidate のパターン自体は既に実装されている。

- `hooks/useCachedTransactions.ts` … メモリキャッシュ → `getDocsFromCache` → 必要時 `getDocsFromServer`
- `hooks/usePaginatedTransactions.ts` … 同様。加えて `updatedAt` による差分読み（incremental）
- 差し替え要否は `lib/readFreshness.ts` の `shouldReadServerForScope` が、世帯の `dataVersion` マーカーとスコープごとの永続化版（`lib/scopeVersionStore.ts`）を比較して判定する

問題は順序である。**キャッシュを読む前に、サーバーへの往復が1回入っている。**

- `useCachedTransactions.ts:147-156` および `usePaginatedTransactions.ts:186-194` で `readHouseholdDataVersionPreferServer(householdId)` を await する
- この関数（`lib/firestore.ts:283-291`）は `readHouseholdDataVersion(householdId, "server")` を await し、**例外が投げられたときだけ** キャッシュへフォールバックする
- ディスクキャッシュを読むのはその後（`useCachedTransactions.ts:174`）

つまり実際の挙動は cache-first ではなく「**サーバー版チェック先行 → その後キャッシュ**」である。初回起動時は `currentVersion === undefined` のため必ずこの往復が走り、タブフォーカス時の再読込でも `refreshMarker` が同じ往復を強制する。電波が悪い環境では `getDocsFromServer` 相当の読み取りがタイムアウトまで粘るため、その待ち時間がそのまま初回表示のレイテンシになる。

検索時はこれに加えて `fetchAll`（全件取得）のコストが乗る。合計金額の集計そのものは `lib/historySearchTotals.ts` の純粋なループなので、ここは律速ではない。

## 決定

**この課題は Issue #9（空メッセージのちらつき）の修正とは分離し、独立したタスクとして扱う。**

Issue #9 は表示ガードだけの局所修正で閉じる（`hooks/useCachedTransactions.ts` に `hasSettled` を追加し、`app/(tabs)/summary.tsx` の空メッセージ判定に使う）。レイテンシ改善はデータ読み取りプロトコルに触るため、混ぜない。

改善案は2つあり、**案Aを先に検討する**。

> **補足（2026-07-25 追記）**: この「案Aを先に」という判断は、後述の「案Bの欠点の再評価」で撤回した。案Bを直接実装する。以下の案A/案Bの記述は、判断の経緯として残す。

### 案A: 版チェックの読み取りに制限時間を設ける（影響範囲が狭い）

`readHouseholdDataVersionPreferServer` のサーバー読みを短いタイムアウトと競争させ、間に合わなければ永続化済みのキャッシュ版で先に描画を進める。読み取り順序は変えない。

- 利点: 変更点が1関数に閉じる。オフライン・低速回線での最悪ケースが有界になる
- 欠点: タイムアウト値が新しいチューニング対象になる。間に合わなかった場合、直前に他端末が行った更新の反映が1テンポ遅れる（次回フォーカスで解消する）
- 未確定: 適切なタイムアウト値。実機での効果測定が必要

### 案B: キャッシュ描画を版チェックより前に出す（本来の cache-first）

ディスクキャッシュを先に読んで描画し、その後に版チェックとサーバー読みをバックグラウンドで走らせる。

- 利点: ユーザー提案そのもの。キャッシュがあれば初回表示が実質ゼロ待ちになる
- 欠点: `scopeVersion` の永続化タイミング、`refreshMarker` の意味、`shouldReadServerForScope` の判定順序をすべて見直す必要がある。オフライン時の固着・古いデータの表示継続に対する影響が広い
- 制約: CLAUDE.md の「オフライン時の固着を避ける」「大量履歴を扱う画面で全件リアルタイム購読を避ける」方針と整合させること

## 理由

- レイテンシは体感上の問題であり、データの正しさや審査には影響しない。バージョン1.0.2のリリースを止める理由がない
- 一方で読み取りプロトコルの変更は、オフライン挙動・世帯間の同期・Firestore読み取り原価に同時に影響する。ちらつき修正と同じコミットに混ぜると、実機で問題が出たときにどちらが原因か切り分けられなくなる
- ユーザーの提案（案B）は設計として正しい方向を指している。ただし現行実装が「半分だけ cache-first」になっている理由（版マーカーによる差分読みで Firestore 読み取り回数を抑える設計。`docs/read-caching-plan.md` および `docs/firestore-read-and-index-plan.md` 参照）を崩さずに実現する必要がある

## 案Bの欠点の再評価（2026-07-25）

初出時に案Bの欠点として「`scopeVersion` の永続化タイミング、`refreshMarker` の意味、`shouldReadServerForScope` の判定順序をすべて見直す必要がある」と書いたが、実装を読み直した結果、**これは見積もり過大だった**。案Bが変えるのは「初回描画をブロックするものは何か」だけで、鮮度プロトコル自体は変わらない。

### 見直し不要と判明した3点

| 当初の懸念 | 再評価 |
| ---------- | ------ |
| `shouldReadServerForScope` の判定順序 | `lib/readFreshness.ts` の同関数は入力をすべて引数で受け取る純関数。呼ぶタイミングが変わっても、関数も引数も変更不要 |
| `scopeVersion` の永続化タイミング | 「サーバー読み成功後に、その読みの直前に取得したマーカー値で stamp する」というルールは案Bでも同じ。マーカー読みとデータ読みの前後関係は変わらないため、stamp の意味は不変 |
| `refreshMarker` の意味 | 「マーカーをサーバーから読み直す」の意味のまま。描画をブロックしなくなるだけ。`forceServer`（pull-to-refresh）は従来どおりキャッシュを飛ばして待たせる |

**オフライン時の固着はむしろ改善する。** 現状はマーカー読みが critical path にいるため、電波が悪いとその待ち時間がそのまま初回表示に乗る。案Bではマーカー読みが背景に回るので、失敗しても遅くても描画が止まらない。

### 実際に設計判断が要る唯一の点: 空状態の判定

ディスクキャッシュが0件のとき、「世帯にデータが無い」のか「まだキャッシュされていない」のかを区別できない。キャッシュ先出しにすると、この曖昧さが表示に直結する。

採用するルール:

- ディスクキャッシュが **1件以上** → その時点で `hasSettled` を立てて描画してよい
- ディスクキャッシュが **0件** → サーバー読みが返るまで `hasSettled` を倒したままにする

これは Issue #9 の修正で `useCachedTransactions` に追加した `hasSettled` と直接噛み合う。案Bで観測可能な挙動が変わるのはここだけなので、実装時はこのルールを明示的にテストする。

### 既知の別問題: スコープ変更中の古いスコープ `setData`（**1.0.2では対応しない**・2026-07-25 決定）

スコープ変更中に進行中の読み込みが、古いスコープのデータを `setData` する窓が現状すでに存在する（`inFlightRef` は直列化するが、進行中クロージャは古い `rangeFrom`/`rangeTo`/`scopeKey` を保持しているため）。集計タブで年を切り替えた直後などに、前の年の数値が一瞬表示されてから正しいものに入れ替わる。

**1.0.2では対応しない判断とした。** 理由:

- **修正の失敗時のほうが症状が重い。** リクエストの世代番号で古い書き込みを捨てる方式になるが、判定を誤ると正しい更新まで捨てて画面が固着する。「一瞬前のスコープが見えて直後に正しくなる」より明確に悪い
- **フックの非同期フロー内部の挙動であり、ユニットテストで固めきれない。** 実機確認が必須だが、EASビルド枠の都合で2026-08-01まで確認できない
- **案Bが作った窓ではなく、1.0.1として配信中のものにも同じ窓がある。** 退行ではないため急がない

1.0.2の実機確認（R9）が通ったあと、1.0.3以降で単独のコミットとして対応する。そのときは実機で「年を高速に切り替える」「検索条件を連続で変える」操作を明示的に確認する。

### 再現条件から確定した適用範囲

実機での体感（2026-07-25、バージョン1.0.2ビルド）は次のとおり切り分けられた。

- **集計タブ・履歴タブ**: スワイプでソフトリセットした直後の初回だけ顕著
- **検索結果の合計表示**: 毎回

前者は案Bが効く条件そのものである。アプリをスワイプ終了しても Firestore のディスクキャッシュと `scopeVersions.json` は残り、消えるのはモジュールスコープの `currentVersionByHousehold` メモ化だけ。したがって再起動直後は「データは手元にあるのに、マーカーのサーバー往復を待ってから描画する」状態になり、往復後はメモ化されるため以降は起きない。`shouldReadServerForScope` が `!hasCachedData` で無条件に `true` を返す（＝キャッシュが空なら順序を変えても速くならない）という制約にも抵触しない。

**後者（検索合計が毎回遅い）は案Bでは解決しない。別原因として扱う。**

確認できた事実:

- 検索を適用すると `readAll` が立ち、`usePaginatedTransactions` の `fetchAll` が `true` になる
- `buildPaginatedTransactionsScopeKey`（`lib/paginatedTransactionsMode.ts:13-22`）は `mode = readAll ? "all" : "page"` をキーに含める。したがって検索の適用/解除で**スコープキーが切り替わり**、通常のページング表示で温まっていた `firstPageCache` には当たらない
- 合計計算そのもの（`lib/historySearchTotals.ts`）は純粋なループなので律速ではない

### 検索合計のタイムラグ: 切り分け結果（2026-07-25）

実機での追加観察により原因が特定できた。

- **カテゴリ等の検索条件を変更した場合 → 即表示**
- **検索条件をクリアしてから再度検索した場合 → タイムラグ発生**

この非対称は実装と一致する。カテゴリ・内訳・お店・メモ・種別は `usePaginatedTransactions` に渡っておらず、`app/(tabs)/history.tsx` 側のクライアントフィルタである。フックの入力は `householdId`・日付範囲・`readAll` のみ。

- 条件変更: フックの入力が変わらない → `refresh` の identity も変わらない → **リロードが発火しない** → クライアント側の再計算だけで完結する
- クリア→再検索: `readAll` が `false` → `true` に反転 → `fetchAll` が反転 → `buildPaginatedTransactionsScopeKey` の `mode` が `page` ↔ `all` で切り替わる → `refresh` identity が変わり `useEffect` が**リロードを発火する**

そしてこのリロードは、`firstPageCache` にヒットして即座に返る場合でも `refresh()` の先頭で無条件に `setLoadingInitial(true)` を立てる。`finally` で `false` に戻るまでに `await`（`loadScopeVersions()`）を挟むため、**1フレーム以上「読み込み中」が描画されうる**。その間 `showSearchTotals`（`viewMode === "list" && shouldReadAllHistory && !paginatedLoadingInitial`）が `false` になり、合計が消えて出直す。

ただしこの経路だけでは体感できる長さにならない可能性がある。`loadScopeVersions()` は初回以降メモ化済みの解決済み Promise を返すため、キャッシュヒット時は `setLoadingInitial(true)` と `finally` の `false` が同一バッチ内の隣接マイクロタスクに収まり、`loadingInitial === true` のフレームが描画されないこともありうる。実機で体感できているということは、**`all` スコープで `shouldReadServerForScope` が `true` を返して実際のサーバー読みが走っている**第2の仮説も残る（`all` スコープが `scopeVersions.json` に stamp されていない場合、`page.version` が `null` になり毎回サーバー読みへ落ちる）。下記の修正で解消しない場合はこちらを疑うこと。

**ただし `!paginatedLoadingInitial` のガード自体は正しい。** リロード中の `items` は直前のスコープのもので、ページング表示から来た場合は先頭ページしか含まない。そこから合計を出すと部分集計を全体の合計として表示してしまう。ガードはその誤表示を防いでいる。

### 採用する方針

検討の過程で方針を2度組み替えた。結論として、**検索合計のタイムラグは独立した課題ではなく、案Bを検索経路にも一様に適用すれば解ける**。

#### 「待つしかない」は誤りだった

当初「手元に全件が無ければ正しい合計は出せないので待つしかない」と整理したが、これは「**サーバーからの**全件が無ければ」の誤りだった。端末のFirestoreディスクキャッシュには過去に同期した取引が保持されており、`getDocsFromCache` を limit なしで実行すればネットワークを触らずローカルだけで全件が返る。ページングモードでキャッシュ読みにも `limit()` を掛けている（`hooks/usePaginatedTransactions.ts` の `queryLimit`）のは実装上の選択であって、ディスクにデータが無いわけではない。

したがって正しい振る舞いは次のとおり。待ちは「サーバー応答待ち」ではなく「ローカル読み完了待ち」になる。

1. 検索が適用されたら、ディスクキャッシュから全件をローカル読みして即座に合計を出す
2. 裏でサーバーに差分を確認し、追加・変更レコードがあれば差し替える

#### 唯一の条件: キャッシュの完全性を stamp で担保する

Firestoreのキャッシュは「この端末が過去に取得したドキュメント」しか持たない。ページングで先頭ページしか閲覧してこなかった端末では、キャッシュにも先頭ページ分しか存在しない。そこから合計を出すと**誤った金額を確定値として表示してしまう**。家計簿として最も避けるべき誤りであり、ここは妥協しない。

見分ける仕組みは既にある。`lib/scopeVersionStore.ts` の stamp が「このスコープを最後にサーバー全件読みした時点の版」を記録している。stamp が無いスコープはキャッシュの完全性を保証できないため、そこだけはサーバー読みを待つ。現行実装でも `page.version` が `null` のとき `shouldReadServerForScope` が `true` を返してサーバー読みへ落ちるため、このガードは既に機能している。

- **そのスコープの初回1回だけ** サーバー全件読みが必要（避けられない）
- `scopeVersions.json` はアプリ再起動でも残るため、**2回目以降は端末を問わず永続的にキャッシュ先出し＋背景差分確認**で動く

#### 優先順位

1. **案Bを両フック（`useCachedTransactions` / `usePaginatedTransactions`）に一様適用する** — マーカー読みを描画の後ろへ移す。集計・履歴・検索のすべての待ちの根がここにある
2. **完全性フラグを導入する** — 「いま手元の `items` が完全な読みの結果か」で `showSearchTotals` を判定し、`!paginatedLoadingInitial` を置き換える。誤表示を防ぐガードであり、同時に全件保持中の不要な点滅も解消する。**定義は R8 を参照すること（stamp の有無だけで判定してはならない）**
3. ~~クリア時に `all` スコープを捨てない~~ — 1と2が入れば再検索時もローカル読みで戻せるため、体感差は小さい。**実施しない**

判定軸は「現在の**日付範囲**に対して全件か」であって「現在の検索条件に対して全件か」ではない。カテゴリ・内訳・お店・メモ・種別はクライアント側フィルタなので、日付範囲の全件が手元にあればどの条件へ変えても合計は正確に算出できる。検索条件の変更が即表示になるのはこのためである。

Issue #9 で `useCachedTransactions` に入れた `hasSettled`（「読み込み中」と「0件と確定してよいか」を分離した）と同じ形の分離である。

## 決定の更新

**案A（タイムアウト）は不要と判断する。** 案Bの実装コストが当初見積もりより小さく、かつ再現条件が案Bの適用範囲と一致したため、タイムアウト値のチューニングという中間段階を挟む理由がなくなった。案Bを直接実装する。

## 実装前に潰すリスク（2026-07-25 レビュー）

案Bは「正しさを先に確定してから描く」を「速く描いてから直す」へ変える。速度と引き換えに**一瞬でも誤った表示を出す経路**が生まれるため、以下は実装とセットで対処する。

### R1（最重要）: 自分の書き込み直後に、書き込み前の状態を見せる

`app/(tabs)/summary.tsx` は `useFocusEffect` で `refreshIfStale()`（＝`refreshMarker: true`）を呼ぶ。記録タブで保存してから集計タブへ移動する流れは本アプリで最も頻度が高い。

- 現行: マーカー読みが先行するため、版の不一致を検出してからディスクキャッシュ（＝自分の書き込みを含む）を描く。書き込み前の状態は表示されない
- 案B適用後: メモリ上の `transactionScopeCache` に残る**書き込み前の配列を先に描画**し、その後に差し替わる。ユーザーは自分がいま記録した金額が反映されていない合計を一瞬見る

家計簿として最も気づかれやすい後退であり、放置できない。

**対策**: 取引の add/update/delete を実行した時点で、その世帯の該当スコープのメモリキャッシュを自分で無効化する（サーバーに聞かなくても、自分が書いたことは分かっている）。無効化後はディスクキャッシュ読みが初回描画になる。Firestoreのディスクキャッシュは未送信の書き込みも含むため、オフラインでも正しい値が出る。ローカル読みのままなので速度も落ちない。

### R2: 合計は一覧より陳腐化に弱い（**実施しない**・2026-07-25 決定）

一覧が1行足りなければ見れば分かるが、合計が数千円ずれていても見て分からない。確定値として読まれる。当初は「背景で再検証している間、合計に『更新中』であることが分かる視覚的手がかりを出す」ことを検討した。

**実施しない判断とした。** 理由:

- この懸念の本体は **R8 で塞がっている**。不確かな合計はそもそも表示しない（`itemsComplete` が false の間は出さない）ため、「古い合計を確定値として読まれる」危険は残っていない
- 残るのは「最新かどうかを能動的に伝える」親切さの領域であり、UIに新しい表示要素を足す変更になる
- EASビルド枠の都合で実機確認ができない期間（2026-08-01まで）に、見た目を確定できないまま新しい表示を入れる価値は低い

必要と判断した場合に備えて、データ側の状況を記録しておく。`useCachedTransactions` は `fromCache` を返しており `app/(tabs)/summary.tsx` で合成済み（ただし現状は `buildBudgetStatusesFromData` に渡るだけで画面表示には使っていない）。`usePaginatedTransactions` は同等の値を公開していないため、`isRevalidating` 相当の追加が必要になる。

### R3: Firestore の LRU GC と stamp の乖離

本リポジトリには `initializeFirestore` / `cacheSizeBytes` の設定が無く、Firestoreは**既定のLRUガベージコレクションが有効**な状態で動いている。キャッシュ上限を超えるとドキュメントが退避されうる一方、`scopeVersions.json` の stamp は「全件読み済み」と主張し続ける。この乖離が起きると、**部分的なキャッシュから全件のつもりの合計を算出する**。

家計簿のテキストDocは小さく、数千件でも数MB程度のため発生確率は低い。ただし対策が安価なので入れる。

**対策**: stamp 時に件数も記録し、キャッシュ読みで得た件数がそれを下回ったら「不完全」と判定してサーバー読みへ落とす。

**件数比較は鮮度の仕組みではない。** サーバー側の追加・更新・削除はすべてマーカー比較で捕まる。判定の順序は次のとおりで、**件数比較に到達するのはマーカーが「何も変わっていない」と言っている場合だけ**である。

1. キャッシュが無い → サーバー読み
2. マーカーが stamp と不一致 → サーバー読み（**追加・更新・削除はここで捕まる**）
3. キャッシュ件数が stamp 時の記録を下回る → サーバー読み（**R3はここだけ**）
4. それ以外 → キャッシュのまま

つまりR3が見るのは「書き込みが1件も起きていないはずなのに手元のドキュメントが減っている」状態に限られる。これはLRU GCによる退避でしか起こらない。ソフトデリートも `deleted: true` を書いた時点でマーカーが進むため、ステップ2で捕まりステップ3には到達しない。

比較には `snapshot.docs.length`（**生のDoc件数**）を使う。`mapActiveTransactions` は `deleted` フラグというドキュメントの中身に依存する変換であり、そこを噛ませると「キャッシュからドキュメントが退避されたか」という測定対象が濁るためである。

判定は `<`（下回ったときだけ）で行う。マーカーが不変のまま件数が増えることは設計上ありえず、増加を検出しても対処のしようがないため。

### R4: 差し替え時のUIジャンプによる誤操作

履歴タブは行タップから編集・削除に入る。背景更新でリストが差し替わる瞬間にタップすると、意図しない取引を開く可能性がある。

**対策**: 内容が実際に変化したときだけ差し替える。スクロール位置を維持する。

### R5: 背景読みの失敗をどう伝えるか

キャッシュ描画に成功し背景のサーバー読みが失敗した場合、ブロッキングなエラー表示は不適切だが、無言で古いデータを出し続けるのも不適切。`error` の扱いを「初回描画に失敗したとき」と「背景更新に失敗したとき」で分ける。

### R6: 完全性の不変条件を incremental パスが保つか（**検証済み・2026-07-25**）

**結論: 不変条件は保たれている。ただし検証の過程で別の問題（下記）が判明した。**

検証した2点:

1. **`fullHistoryScopeKey` の stamp 借用は健全。** 借用元は `buildPaginatedTransactionsScopeKey(householdId, { from: null, to: null }, true)`＝「全期間・`all` モード」のスコープに固定されている（`hooks/usePaginatedTransactions.ts:138-144`）。全期間を全件読みしていれば任意の部分期間もその読みに含まれるため、部分期間スコープが借りても完全性は崩れない。またフォールバックは `fetchAll` が真のときだけ発火する。
2. **incremental 読みは取りこぼさない。** stamp に使う `currentVersion` は**データ読みより前**に取得したマーカー値であるため、stamp がデータ実体より新しくなることはない。マーカー読みとデータ読みの間に書き込みが挟まった場合は「取得済みの変更を次回もう一度取りに行く」方向にズレるだけで、`mergeTransactionCacheItems` が冪等に吸収する。**取りこぼす方向には倒れない。**

### R6-b（新規発見）: `page` スコープは部分読みなのに stamp されている

`hooks/usePaginatedTransactions.ts:301-321` はサーバー読みの直後に無条件で `setPersistedScopeVersion(scopeKey, ...)` を呼ぶ。この読みは `queryLimit == null ? base : query(base, limit(queryLimit))` であり、**ページングモードでは `limit()` 付き＝先頭ページだけの読み**である。

つまり `page` スコープは、部分読みであるにもかかわらず stamp されている。**R8 の警告は理屈上の懸念ではなく、すでに全端末の `scopeVersions.json` に「部分読みなのに stamp 済み」のエントリが実在している。** stamp ベースの完全性判定を実装すると、初日から `page` スコープを「完全」と誤認する。

**救い**: mode がスコープキーに encode されている（`:page:` / `:all:`）。`all` モードは `queryLimit = null` のため、stamp されるのは常に完全読みのあとである。

**したがって永続 stamp は「`all` モードのキーに限り、完全性の十分条件」として使える。** 必要条件ではない（R8 のマーカー null 問題があるため）。この非対称を実装で明示すること。

### R7: 新規世帯・初回インストールは最も遅い経路のまま

空状態ルール（キャッシュ0件→サーバー読みまで待つ）と `!hasCachedData` の扱いにより、データが無い世帯は必ずサーバー待ちになる。現行から悪化はしないが改善もしない。**App Store審査員が新規アカウントで触るのはこの経路である**点は認識しておく。

### R8（最重要）: 完全性フラグを stamp の有無で判定してはならない

`lib/scopeVersionStore.ts` の `setPersistedScopeVersion` は `if (version == null) return;` で **null を記録しない**。`version` の元になる `currentVersion` が null になる経路が実在する。

- `households/{id}/meta/dataVersion` Doc がまだ存在しない世帯
- **オフライン時**: `readHouseholdDataVersionPreferServer` のサーバー読みが throw し、キャッシュ読みも未キャッシュなら `null`

この場合 stamp は永久に記録されない。したがって「stamp 済みか」だけで `showSearchTotals` を判定すると、**該当世帯では検索合計が一度も表示されない**。現行の `!paginatedLoadingInitial` なら表示されるため、これは明確な後退である。

**正しい定義**: 完全性フラグは「**いま `items` に入っている配列が、完全な読みの結果であるか**」をフックの状態として読み取り時に立てる。

- サーバーの `fetchAll` 読みが完了した → その `items` は完全（**stamp の成否と無関係**）
- 完全と分かっているスコープのキャッシュ読みで得た → 完全
- ページング読み（`limit` 付き）で得た → 不完全

stamp はセッションを跨いで「前回サーバー全件読みした」ことを引き継ぐための**永続化手段**であって、完全性の唯一の根拠ではない。両者を混同しないこと。

### R9: 受け入れ基準を実装前に決める

レイテンシ改善は「体感で速くなった」では検証できない。本ADRに至る調査では「これで直る」という見立てが3回外れている（集計タブの初回修正、完全性フラグで検索合計が直る、スコープキー設計が本命）。実装前に観測可能な合格条件を固定する。

> ⚠️ **実施順序に注意。** 下表のうち「新規インストール直後」を前提とする3項目は、**キャッシュがまっさらな状態でしか再現できない**。アプリを普通に使うとスコープに stamp が付き、以後は同じ状態を作れない（作り直すには再インストールが必要）。**インストールとサインインの直後に、まずその3項目から実施すること。**
>
> 1. 履歴タブを先に開く → その直後に集計タブを開く（O-5）
> 2. そのまま検索を実行する（初回インストール直後の検索）
> 3. 一度も開いていない年を機内モードで開く（O-5 の案内文言）
>
> その後: 普通に使ってキャッシュを温める → スワイプ終了して再起動 → レイテンシ関連 → 記録との往復 → 検索の適用/解除 → 機内モード関連、の順で進める。

| シナリオ | 合格条件 |
| -------- | -------- |
| ソフトリセット → 集計タブを開く | `ProgressOverlay` を一度も挟まずに前回の数値が描画される |
| ソフトリセット → 履歴タブを開く | 同上。空メッセージも出ない |
| 検索クリア → 再検索 | 合計が消えずに表示され続ける |
| 記録タブで保存 → 集計タブへ移動 | **最初の描画時点で**、記録した金額が反映されている（R1の検証） |
| 初回インストール直後に検索 | 合計が出るまで待つ。ただし誤った合計は一度も表示しない |
| 機内モードで各タブを開く | キャッシュがあれば即描画。固着しない |
| 機内モードのまま検索する | **過去に全件読みしたことのあるスコープなら**合計が表示される。一度も全件読みしていないスコープでは合計を出さない（誤った金額を確定値として出さないための意図した挙動であり、不具合ではない） |
| 取引を1件削除してから履歴・集計を開く | 余計な全件サーバー読みが走らない（R3 の誤検知が無いこと） |
| ページング表示のまま履歴を開き直す | `page` スコープの stamp を根拠に合計を出さない（R6-b） |
| 機内モードで数件記録してから、履歴・集計を何度か行き来する | 記録が反映されている。リストのスクロール位置が勝手に動かない（O-1） |
| **機内モードで履歴のレコードを削除する** | タブを切り替えなくても、その場で一覧から消える（O-6） |
| 機内モードで履歴のレコードを編集して保存する | タブを切り替えなくても、その場で一覧に反映される（O-6） |
| 機内モードで各タブを開閉する（dev-clientで実施） | コンソールに未処理の Promise 拒否が出ない（O-2） |
| 履歴を下までスクロールして追加読み込みが走っている最中に、検索を適用する | 検索が反映される。無視されない（O-4） |
| **新規インストール後、先に履歴タブを開いてから集計タブを開く** | 途中で小さい金額が表示されてから正しい金額に飛ぶ、という挙動が起きない（O-5） |
| 機内モードのまま、一度も開いていない年の集計タブを開く | 「記録がありません」ではなく「集計を表示できません」の案内が出る（O-5） |
| 通常の回線と機内モードで、これまでどおり動く | 上限時間の導入による退行が無いこと。**「電波が弱い状態」は再現手段が無いため受け入れ基準にしない。** 上限時間の仕組み自体は `lib/readTimeout.test.ts` で担保する（O-3） |

### R10: 順序判断を純関数へ切り出す

案Bの本体は非同期処理の順序であり、フックに埋め込んだままではユニットテストが書けない。`shouldReadServerForScope` と同じ形で「次に何を読むべきか」を返す純関数へ切り出し、順序と分岐をテストで固定する。

### R11: R2の「更新中」表示に新しいフラグを作らない（**R2の不実施により不要**）

`useCachedTransactions` は既に `fromCache` を返しており、`app/(tabs)/summary.tsx` で他の購読の `fromCache` と合成済み。R2の視覚的手がかりはこれを使う想定だったが、R2を実施しない判断としたため本項も不要になった。

## build 39 との差分レビュー（2026-07-26）

TestFlight配布中の build 39（`04a07ab`）と実装後の状態を突き合わせ、退行と新たなリスクを洗った。結果として2件を修正し、2件は対応しない判断とした。

### 修正した: stamp が無いスコープでキャッシュを信用していた

`shouldReadServerForScope` は `scopeVersion`（stamp）と `currentDataVersion`（マーカー）を比較する。両方が `null` のとき `null !== null` が `false` になり、**このスコープを一度も全件読みしていないにもかかわらずキャッシュを採用していた**。

stamp が無いということは「キャッシュに全件が入っているのか、過去のページング読みの一部なのか判断する材料が無い」状態である。`scopeVersion == null` なら無条件でサーバーを読むように変更した。

> なお当初これを「オフラインで検索合計が出なくなる退行」として起票したが、**誤りだった**。stamp 済みのスコープならオフラインでも合計は表示される。未 stamp のスコープで合計を出さないのは、誤った金額を確定値として表示しないための正しい挙動である。build 39 はそこで合計を出していたが、それが危険な側だった。受け入れ基準表の該当行の文言を訂正した。

### 修正した: 等価判定のコスト

R4 の `areTransactionListsEquivalent` は `for...in` でキーを走査していた。全件スコープでは「変化なし」が最も多く、かつ早期脱出できない最も重い経路になる。`for...in` はプロトタイプチェーンを辿るため、数千件×毎回の再検証では無視できない。

比較対象を明示列挙して単純ループへ変更した。**単純な列挙は追従漏れが起きると「変更を検出できず画面が古いまま固まる」という現状より悪い壊れ方をする**ため、`Record<keyof Transaction, true>` として宣言し、`Transaction` にフィールドが増えたら型エラーになるようにした。全フィールドの変更が検出されることをテストでも二重に固定している。

### 対応しない: `scopeVersions.json` の形式変更はロールバック不可

旧形式（文字列）の読み込みには対応しているが、逆は無い。1.0.2 を入れた端末を 1.0.1 に戻すと、旧コードはオブジェクトを文字列として比較するため常に不一致となり、毎回サーバー読みになる。壊れはしないが読み取り原価が上がる。

App Store 経由のダウングレードは通常できず、ロールバック運用も想定していないため対応しない。ただし**1.0.2 で問題が出ても「1.0.1 に戻す」で綺麗には戻らない**点は認識しておく。

### 対応しない: 全件がソフトデリートされたスコープの空メッセージ

生のDoc件数が 0 より大きく、`mapActiveTransactions` で全件除外されるスコープでは、描画時に `loadingInitial` が倒れて「記録がありません」が一瞬表示される。build 39 では出なかった。実害が無く、発生条件も極めて稀なため対応しない。

## オフライン観点のレビュー（2026-07-26）

本アプリはオフライン利用が十分想定される（電波の悪い店内での記録など）。その観点で両フックを通読し、3件を修正した。

**前提として、案Bはオフラインで明確に効いている。** 初回描画がネットワークを待たなくなり、オフライン記録直後も R1 がメモリキャッシュを捨ててディスクを読むため、自分の記録が入った状態で即座に描画される。以下はその上で残っていた問題。

### O-1: 未送信の書き込みがあると R4 の等価判定が常に「変化あり」になる

`lib/firestore.ts` の `toISOString` は値が無いとき**その時点の現在時刻**を返す。未送信の書き込みはサーバータイムスタンプが未確定で `null` として読まれるため、**読み直すたびに `createdAt` が変わる**。結果、オフラインで記録が溜まっている間は必ず「内容が変わった」と判定され、フォーカスのたびにリストが再描画される。R4 が防ごうとしたスクロール跳ねとタップずれが、オフラインでだけ復活していた。

**対応**: `createdAt` を比較対象から外す。型は `Exclude<keyof Transaction, "createdAt">` として宣言し、他のフィールドが増えたときの追従は引き続き型が強制する。

**残る代償（許容した）**: `createdAt` だけが変わった差分を検出しなくなる。実際に起きるのは「未送信の書き込みがサーバーに確定した」瞬間だけで、そのとき保持され続けるのは生成時にでっち上げた現在時刻である。この値は同日内の並び替え（`lib/historyList.ts` / `lib/transactionCacheMerge.ts`）とお店候補の新しさ（`lib/storeOptions.ts`）に使われるが、未確定の書き込みについては元から近似値でしかなく、実データより新しい側に倒れる点も変わらない。画面表示には使っていない（`app/` 配下に参照なし）。

### O-2: `usePaginatedTransactions` にエラーを受ける場所が無かった

`finally` はあるが `catch` が無く、サーバー読みの失敗がそのまま未処理の Promise 拒否になっていた。`finally` は走るので固着はしないが、**オフラインでフォーカスするたびに拒否が発生する**。開発ビルドでの機内モード確認でノイズになる。`useCachedTransactions` 側は R5 で対応済みであり、非対称だった。

**対応**: `catch` を追加し、画面はキャッシュ描画のまま据え置いて次のフォーカスで再試行する。このフックにはエラー表示の経路が無いため、`__DEV__` 限定で `console.warn` に出す。

### O-3: 応答が返らないサーバー読みで操作が無反応になる

両フックは `inFlightRef` で読み込みを直列化している。`getDocsFromServer` 相当の読み取りは、完全なオフラインなら即座に失敗するが、**電波が中途半端なときは応答も失敗もせずに待ち続けることがある**。そうなると `inFlightRef` が立ったままになり、以降の要求は予約キューに積まれるだけで実行されない。**年の切り替えも検索の適用/解除も無反応になる。**

案B以前は「描画前に待つ」だったためスピナーが出続けて分かりやすかったが、案B後は**画面には正常にデータが出ているのに操作だけ効かない**状態になる。見た目が正常なぶん分かりにくい。CLAUDE.md の「オフライン時の固着を避ける」に該当する。書き込み側には `lib/pendingWrite.ts` の `waitForPendingWrite` があるが、読み取り側に同等の仕組みが無かった。

**対応**: `lib/readTimeout.ts` の `withReadTimeout` を追加し、両フックのすべてのサーバー読み（マーカー・差分・全件）に上限時間（15秒）を設ける。

設計上の注意点:

- **上限は固着回避のための値であり、遅い回線を諦めるための値ではない。** 短くすると、時間はかかるが成功したはずの読み取りを捨てて、遅い回線でいつまでも最新化されなくなる
- **上限に達したマーカー値をメモ化しない。** ここで `null` を書き込むと、1回の応答なしがセッション中ずっと「マーカーは null」として残る
- **上限に達したあとで届いた失敗を未処理の拒否にしない。** `waitForPendingWrite` と同じくフラグで吸収する。これを怠ると O-2 で塞いだ穴を自分で開け直すことになる
- **描画済みならマーカー上限到達時にそこで終える。** 鮮度を確認できないまま読み直さない。次のフォーカスで再試行する
- **既知の代償**: 上限に達しても Firestore 側の処理は中断できない（キャンセル手段が無い）。遅れて完了した読み取りにも課金される可能性があり、再試行と合わせて読み取り回数が増えうる。固着した画面より許容できると判断した

**検証方法の制約**: 「電波が中途半端な状態」は意図的に作れないため、**受け入れ基準にしない**。上限時間の仕組み自体は `lib/readTimeout.test.ts` で担保し（上限到達、上限内の成功・失敗、上限後に届いた成功・失敗の吸収）、実機では「通常の回線と機内モードで退行が無いこと」だけを確認する。どうしても実機で再現したい場合は、Wi-Fi に接続したままルーターのWAN側を切る（接続はあるが応答が無い状態）を作れば近い状況になる。

### O-4: `loadMore` に同じ穴が3つ残っていた

`refresh` を直したあとも、追加読み込み（`loadMore`）には手が入っていなかった。同じ `inFlightRef` を握るため、影響は `refresh` と同じところに出る。

1. **上限時間が無い** — 応答が返らないと `inFlightRef` を握ったままになり、年の切り替えや検索の適用が止まる（O-3 と同じ）
2. **`catch` が無い** — 失敗が未処理の Promise 拒否になる（O-2 と同じ）
3. **`pendingReloadRef` を消化していない** — `refresh` の `finally` は予約された再読み込みを消化するが、`loadMore` の `finally` にはその処理が無い。**追加読み込み中に年の切り替えや検索の適用を行うと、その要求は予約キューに積まれたまま誰にも実行されずに捨てられる**

3つ目は上限時間とは無関係の既存バグである。履歴をスクロールしながら検索を適用する、という現実的な操作で踏む。

**対応**: 3点とも `refresh` と同じ形で塞いだ。

全サーバー読み取り地点を洗い直し、未対応が無いことを確認した。`hooks/useCachedStoreOptions.ts` はキャッシュ読みのみ、`hooks/useFirestore.ts` は `onSnapshot` の購読で `inFlightRef` を握らないため対象外。

### O-5: 集計タブに完全性のガードが無かった

検索合計には R8 で `itemsComplete` を入れたが、**集計タブは `transactionData` をそのまま集計していた**。ガードが無い。

踏む経路:

1. インストール直後、先に履歴タブを開く → 直近100件が Firestore のディスクキャッシュに入る
2. 集計タブを開く → `getDocsFromCache(その年の範囲)` が、その100件のうち該当年のぶん（例: 80件）を返す
3. **80件で計算した合計が表示される**（実際は800件ある年）
4. マーカー確認 → 未 stamp → サーバー全件読み → 正しい値へ差し替わる

支出が ¥45,000 と出てから ¥380,000 に飛ぶ、という見え方になる。**1.0.1（配信中）にも同じ経路がある**（旧実装もキャッシュ描画 → サーバー読みの順）。案Bが作ったものではないが、家計簿として最も避けたい「誤った合計の表示」に該当するため対応した。

**対応**: `useCachedTransactions` に `isComplete` を追加し、集計の描画をそれで判定する。

- サーバーから読み切った直後 → 完全（stamp の保存可否と無関係）
- メモリキャッシュのうちサーバー由来のもの（`fromCache === false`）→ 完全
- ディスクキャッシュ由来 → stamp があるときだけ完全
- 全件と分かっているものを描けていない間は `loading` を立て、オーバーレイを出す

一覧（履歴カレンダー）は部分的でも実害が無いため、`data` の描画自体は従来どおり行う。判断は消費側に委ねる形にした。

**確認できないときの表示**: 「記録がありません」は事実と違う（記録はあるが端末に届いていない）ため、専用の案内に分ける。

> 集計を表示できません
> この期間の記録が、まだすべてこの端末に届いていません。オンラインのときにもう一度開くと集計できます。

「キャッシュ」「同期」などの内部用語は使わない。ユーザーが取れる行動（オンラインで開き直す）を明示する。

**この表示が出る条件**: そのスコープを一度もオンラインで開いていない端末で、オフラインのまま集計タブを開いた場合。stamp は端末に永続するため、一度オンラインで開けば以後は出ない。

### O-6: 自分の書き込み直後に `forceServer` で読み直していた（実機で発見・2026-07-26）

dev-clientでの実機確認中に発見。**機内モードで履歴タブのレコードを削除しても、一覧に反映されない。** タブを切り替えて戻ると消えている。

原因は `app/(tabs)/history.tsx` の書き込み後の再読込にあった。削除・編集・一括コピーの後に `refresh()`（＝`{ forceServer: true, refreshMarker: true }`）を呼んでいた。`forceServer` は `pickFirstPaintSource` が `"none"` を返す指定であり、**キャッシュを一切使わずサーバーだけを読む**。オフラインではその読み取りが失敗するため `setItems` が一度も呼ばれず、画面は書き込み前のまま残る。タブを切り替えると `refreshIfStale`（キャッシュ経路）が走り、そこで初めて反映される。

**`forceServer` の使いどころが逆になっていた。** 本来「最新をサーバーから取りに行きたい」プルリフレッシュは `refreshIfStale` を使っており、`forceServer` はローカル書き込み直後という**最も使ってはいけない場所**でだけ使われていた。書き込みは既にローカルのキャッシュへ反映されているのだから、サーバーだけを見る理由が無い。

**対応**: 書き込み後の3箇所（削除・編集保存・一括コピー）を `refreshIfStale` に変更した。マーカーは自分の書き込みで進んでいるため、オンラインなら `shouldReadServerForScope` が不一致を検出してサーバーから読み直す。鮮度は変わらず、オフラインでも画面が更新される。

`refresh`（`forceServer`）はどの画面からも呼ばれなくなったが、フックのAPIとしては残す。

> **同種の確認**: 新規記録が履歴タブに反映される経路は、書き込み後の明示的な再読込ではなく `useFocusEffect` → `refreshIfStale` を通っていたため、この不具合の影響を受けていなかった。実機でも「機内モードで記録 → 履歴タブ → すぐ出る」ことを確認済み。**症状が作成と削除で分かれていたのは、この経路の違いによる。**

## O-7: 初回表示レイテンシの真因（実測で特定・2026-07-26）

案B（キャッシュ先出し）を入れても、実機では履歴タブの初回描画に **10.6秒**かかっていた。`__DEV__` 限定の計測を仕込んで各フェーズの実時間を取り、原因を特定した。**推測では4回続けて外し、計測して初めて分かった。**

### 計測で分かったこと

初回描画までの内訳（取引 11,808件の実データ）:

```text
storeOptions キャッシュ読み 開始: 0ms   ← 同時に5本発行されていた
storeOptions キャッシュ読み 完了 (11808件): 3008ms
storeOptions キャッシュ読み 完了 (11808件): 5223ms
storeOptions キャッシュ読み 完了 (11808件): 5980ms
storeOptions キャッシュ読み 完了 (11808件): 8258ms
storeOptions キャッシュ読み 完了 (11808件): 10491ms
paginated  ディスクキャッシュ読み 完了 (479件): 10621ms  ← 直後に完了
```

**真因は `hooks/useCachedStoreOptions.ts` だった。** お店候補を作るために、`limit` も日付範囲も付けずに取引を全件読んでいた。1回あたり約3秒。しかもこのフックは記録タブと履歴タブの両方で使われ、マウント時・フォーカス時・一覧件数の変化時にそれぞれ発火するため、**同じ全件読みが同時に5本発行され、直列処理で10.5秒**になっていた。履歴リストの読みはその後ろで待っていただけだった。

`mapActiveTransactions` は 11,791件で約100ms と速く、ボトルネックではなかった。

### 途中で捨てた仮説（記録として残す）

計測前に立てた仮説はいずれも外れた。同種の調査で同じ回り道をしないよう残す。

| 仮説 | 実測結果 |
| ---- | -------- |
| `getDocsFromCache` 自体が遅い | 集計の年スコープは1131件を286msで返しており、遅くない |
| Firestore の単一キューで順番待ち | 部分的には正しいが、待たせていた主体は別だった |
| `limit` 付きクエリがローカルインデックスを使えず全走査する | `limit` を外しても改善しなかった |
| 取引件数（11,806件）に比例している | 日付窓で479件に減らしても時間は変わらなかった |

**測っていたのは Firestore の速度ではなく、JSスレッドが解放されるまでの時間だった。** 23件の読みと479件の読みが毎回2〜3ms差で「完了」していたのがその兆候で、両方のコールバックがJSスレッドの解放後に同じタイミングで走っていた。件数で説明できない時点で計測方法を疑うべきだった。

### 対応

1. **お店候補の元データを直近12ヶ月に限定**（`STORE_SOURCE_WINDOW_MONTHS`）。候補は「最近このカテゴリで使ったお店」を出すためのもので、全期間を読む必要がない
2. **取得結果をモジュール内で共有**し、重複呼び出しを1本にまとめる。端末自身の書き込み（`localWriteEpoch`）があれば作り直す。サインアウト・世帯切替では `clearStoreSourceCache()` で破棄する
3. **履歴リストのキャッシュ読みに日付の窓**を段階的に適用（3ヶ月 → 12ヶ月 → 36ヶ月 → 全期間）。先頭ページ分そろった時点で打ち切る。日付範囲指定なしのページングモードだけが対象で、全件モードや範囲つき検索には適用しない
4. **世帯ID解決をプロセス内で1回に**（`resolveHouseholdIdOnce`）。3画面がそれぞれ `getHouseholdId()` を呼び、そのたびにサーバーへ2往復していた

### 結果

| 項目 | 修正前 | 修正後 |
| ---- | ------ | ------ |
| 履歴タブの初回描画 | 10,622ms | **243ms** |
| 以降の再読込 | 3,200〜5,300ms | 400〜640ms |
| 集計タブのキャッシュ読み | 1,561ms | 244ms |

### 残した代償

- **12ヶ月より前にしか使っていないお店は候補に出ない。** 手入力は従来どおり可能で、影響は候補の並びに限られる。不足するようなら期間を延ばせるが、延ばすほど遅くなる関係にある
- 履歴リストの `hasMore` は「窓が全期間に届いていなければ続きあり」と安全側に倒している。余分に `loadMore` が走っても `mergeTransactionCacheItems` が重複を排除する
- `loadMore` の連結を `mergeTransactionCacheItems` へ変更した。単純連結のままだと、差分マージで過去日付の取引が先頭ページに入ったとき並び順が崩れる
