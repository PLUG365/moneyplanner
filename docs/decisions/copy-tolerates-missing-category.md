# 一括コピーはカテゴリが現存しなくても成立させる（2026-08-07）

## 背景

履歴タブの長押し一括コピーは、コピー元のカテゴリ/内訳を現行マスタへ再解決してから
登録する（`lib/transactionCopy.ts` の `resolveTransactionCopyTarget`）。再解決は
「ID一致 → 同種別のカテゴリ名一致」の順で試し、どちらも当たらない場合は `null` を返し、
呼び出し側（`app/(tabs)/history.tsx`）がその記録を未コピー扱いにして
「一部コピーされませんでした」モーダルに並べていた。

つまり、**カテゴリを削除・改名した後の古い記録はコピーできない**。ユーザーから見ると、
履歴では普通に表示・編集できている記録が、コピーのときだけ理由の分からないエラーになる
（Issue #12）。

口座については同じ状況で既にフォールバックしており（`accountFallback`。現存しなければ
既定口座で登録して件数を通知）、カテゴリだけが失敗扱いという非対称でもあった。

## 決定

`resolveTransactionCopyTarget` は `null` を返さない。カテゴリを再解決できない場合は、
**コピー元の `categoryId` と内訳IDをそのまま引き継いで**コピーを成立させ、
`categoryFallback: true` で呼び出し側に知らせる。

コピー先のスナップショット名（`categoryNameSnapshot` 等）は、既存の
「現行マスタで引けなければ取引スナップショットへフォールバック」の組み立てがそのまま効くため、
コピー元の表示名が引き継がれる。

`categoryId` を空にせず引き継ぐのは、集計のキー生成（`buildCategorySummaryKey`）が
`categoryId` を優先するため。IDを捨てると、同じ削除済みカテゴリの記録が
コピー前後で別グループに割れる。

## 根拠

取引はカテゴリ削除後もスナップショットで表示・CSV出力できる、というのがこのアプリの
既定方針（PLAN.md「マスタ変更とスナップショット運用方針」）。宙に浮いた `categoryId` を
持つ取引は、削除やインポートで通常発生する想定内の状態であり、コピーで新しく作っても
不整合は増えない。Firestore Rules もサブコレクションのフィールド型検証をしないため
（`allow read, write: if activeMember`）、書き込みは通る。

## 「一部コピーされませんでした」モーダルの扱い

削除せず、**保存自体に失敗した記録**のための表示として残した。あわせて、1件の書き込み失敗が
ループ全体を巻き込まないよう `addTransaction` の呼び出しを try/catch で包み、失敗分だけを
モーダルへ回すようにした。従来は例外がそのまま抜けて、残りの選択記録が処理されないまま
Promise が reject していた。

完了通知の組み立ては `lib/transactionCopyResult.ts` の `buildBulkCopyAlert` に分離して
テストを付けた（画面側に散っていた4分岐の文言生成をまとめたもの）。

## 採用しなかった案

- **未分類カテゴリへ寄せる**: コピー後の記録から元のカテゴリ名が失われ、履歴の証跡性を
  下げる。スナップショット方針とも逆行する。
- **コピー前にカテゴリ再作成を促す**: 一括コピーは「先月と同じ固定費をまとめて登録する」
  用途が中心で、そこでマスタ整備を強制すると操作が止まる。
- **既定カテゴリへフォールバック**: 口座と違い、カテゴリは金額の意味そのもの。
  黙って別カテゴリに付け替えると集計が静かに狂う。

## 影響

- Firestore Rules・データモデルの変更なし。
- `CopyTarget` に `categoryFallback` が増えた（型変更。参照は履歴タブのみ）。
- 実機確認は、カテゴリを削除した後にその記録を一括コピーして、カテゴリ名が引き継がれること、
  完了通知に「カテゴリが存在しないN件」が出ることを見る。

## 追記（2026-08-29）: 編集モーダルを開いた際の先頭カテゴリへの誤フォールバックを修正

CSVインポートで未分類（`categoryId: null`、`categoryNameSnapshot` のみ保持）になった収入記録を
履歴の編集モーダルで開くと、`syncEditCategories`（`app/(tabs)/history.tsx`）がカテゴリを
再解決できない場合に**マスタの先頭カテゴリへ無条件でフォールバック**していた。メモなど別項目
だけ直したつもりで保存すると、記録が黙って無関係なカテゴリ（例: 「副業」のはずが先頭の
「給与所得」）へ変わってしまう不具合（Issue報告なし、実利用中に発覚）。

原因は本ADRが対象とする一括コピーの `resolveTransactionCopyTarget` ではなく、編集モーダルの
初期値計算だけが持っていた別経路の欠陥だった。一括コピー自体、CSVインポート
（`lib/csvImportResolve.ts`）はいずれも「解決できなければ `null`/元IDのまま」を守れていた。

`resolveEditInitialCategoryId`（`lib/transactionCopy.ts`）を切り出し、記録由来の指定
（`preferredCategoryId`）があるのに再解決できない場合は元のID/`null`をそのまま保持するよう変更。
先頭カテゴリへのフォールバックは、種別変更など記録由来の指定が一切ない場合だけに限定した。

あわせて、カテゴリ名の同名一致（`resolveTransactionMasterSelection`）に、内訳側は元から
あった「空文字では一致を試みない」ガードを追加。空/破損データがカテゴリ名の同名一致で
別カテゴリに誤って結び付くのを防ぐ（実害は未確認の防御的修正）。

「削除して同名で作り直すと再接続する」という同名一致の挙動自体（コピー元カテゴリが真に
存在しない場合ではなく、たまたま同名の別カテゴリを新規作成した場合に静かに付け替わりうる
リスク）は本追記の対象外。ユーザー判断で見送り、既知の設計として残す。
